# gayhydra-dropper

A small Go program that enumerates mounted filesystems and drops a calling-card file (`1337.txt`) on each writable one. Its user-visible strings are XOR-obfuscated with single-byte key `0x5A` so the puzzle for a student is the deobfuscation, not the dispatch logic.

## Why this sample exists

Two reasons:

1. **A real-but-harmless RE training target.** GayHydra / upstream Ghidra users need something to practice on that's small enough to read end-to-end (~150 LOC), behaves like the kind of binary they'd actually be asked to analyze (small dropper with mildly obfuscated strings), and is safe to run outside a VM (fails closed on permission denials, only writes where the invoking user can write). Existing samples under `Ghidra/Extensions/sample/` are *framework extension* samples (Java) — this is the first *RE target* sample (a binary-to-be-reversed).

2. **A smoke test for new GayHydra builds.** The sample's decompiled `main.main` should always show four byte-by-byte XOR loops with the literal constant `0x5A`. If a new build's decompiler can no longer surface that constant — or its Go analyzer crashes before applying symbols, or the headless launcher refuses to start — the smoke test fails and we've caught a regression before users hit it.

## Behavior

- Parses `/proc/mounts`.
- Skips pseudo-filesystems (`proc`, `sysfs`, `tmpfs`, `cgroup*`, `overlay`, `squashfs`, etc.) and any mount with the `ro` option.
- Writes `1337.txt` containing `File generated by GayHydra.\n` (mode 0644) at the root of each remaining mount.
- Prints `dropped: <path>` per success and a final `written / skipped / failed` summary.

Continues past errors rather than stopping, so as a non-root user it typically writes only to the home filesystem (and fails closed on `/`, `/boot`, etc.).

## Build

```bash
cd samples/re-targets/gayhydra-dropper
go build -ldflags="-s -w" -o gh-dropper-stripped .
```

`-s -w` strips the ELF symbol table and DWARF, matching the real-world scenario where you're handed a binary with no names. The Go compiler also inlines tiny helpers — in this case `main.deobfuscate` gets inlined into `main.main`, so all four XOR loops appear in `main.main` rather than as separate functions.

Build an unstripped variant alongside it if you want to compare:

```bash
go build -o gh-dropper-unstripped .
go tool nm gh-dropper-unstripped | grep main\.
```

## Using the sample to test a new GayHydra build

The test is: load the stripped binary in GayHydra, decompile `main.main`, and confirm the literal constant `0x5A` appears in at least one XOR expression.

A reproducible headless recipe — the included post-script automates the check:

```bash
# 1. Prereqs: a JDK that GayHydra accepts (currently JDK 21; portable Temurin works).
export JAVA_HOME=/path/to/jdk-21
export PATH=$JAVA_HOME/bin:$PATH

# 2. Build the stripped sample (see Build above).

# 3. Run analyzeHeadless against it, with the bundled post-script.
mkdir -p /tmp/gh-project
<gayhydra-install>/support/analyzeHeadless /tmp/gh-project DropperRE \
  -import ./gh-dropper-stripped \
  -postScript DumpDeobfuscate.java \
  -scriptPath ./scripts \
  -deleteProject
```

### Expected output

```
DumpDeobfuscate.java> decompiling FUN_004a4480 @ 004a4480
DumpDeobfuscate.java> decompiled C body written to /tmp/main_main_decompiled.c (10303 bytes)
DumpDeobfuscate.java> SUMMARY: 289 lines decompiled; 4 line(s) reference XOR key 0x5A
DumpDeobfuscate.java> RESULT: PASS — XOR key 0x5A visible in decompiler output
```

The decompiler should reduce each inlined `deobfuscate` loop to a line shaped like:

```c
puVar3[uVar10] = *(byte *)((int)pvVar9 + uVar10) ^ 0x5a;
```

Four such lines is the expected count (filename, payload, mounts path, fstype skip list). The address `0x4a4480` is the entry point of `main.main` for a sample built with Go 1.26 on linux/amd64; if a future Go version reshuffles the layout, update the address in `scripts/DumpDeobfuscate.java`.

## Known issues this sample caught on first run

The very first dogfood run against the v26.1.6 prebuilt — exactly the scenario this sample exists to exercise — surfaced three real bugs:

1. **Go 1.26 analyzer crash** — `GolangSymbolAnalyzer` throws `java.io.EOFException: Invalid index: 549696843` from `GoUncommonType` introspection on Go 1.26 binaries. Partial analysis succeeds but no Go function name labels are applied, so `main.main` and friends show up as `FUN_004a4480`. The sample's post-script works around this by addressing `main.main` by absolute address.

2. **JDK 21.0.10+ headless launch fails** — `Djdk.serialFilterFactory` is set via `support/launch.properties`, but `ObjectInputFilter$Config.setSerialFilterFactory` in JDK 21.0.10+ allows only one call, and Ghidra's `GhidraSerialFilterFactory.getOrInstallInstance` tries to install programmatically as well. Result: `IllegalStateException: Serial filter factory has previously been instantiated` and headless never starts. Workaround: comment out the `VMARGS=-Djdk.serialFilterFactory=...` line in `launch.properties`.

3. **v26.1.7 release workflow failure** — `gradle/sbom.gradle:29` passes a `String` to the cyclonedx plugin's `schemaVersion` property, which the plugin's current version expects as `org.cyclonedx.Version`. The v26.1.7 release has no published artifacts as a result; v26.1.6 was the last successful build.

Each of these regressions would have been caught earlier if this sample had been run as part of release gating. That's a reasonable next step — wire `DumpDeobfuscate.java` into the release workflow as a post-build smoke check.

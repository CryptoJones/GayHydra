# Software Bill of Materials (SBOM)

*Addresses Rec 21 of the 2026-05-21 principal-architect audit.*

## What ships

Every release zip includes a CycloneDX SBOM at:

```
support/sbom/bom.json
support/sbom/bom.xml
```

The SBOM enumerates every JAR Ghidra ships with: group, artifact,
version, hash, and license. Enterprise consumers, vulnerability
scanners, and downstream packagers can read these files directly.

## Format & spec

- **CycloneDX 1.5** — the latest stable schema as of 2026-05-21.
- **JSON + XML** — both formats ship. Downstream tooling preference
  varies; we publish both rather than guessing.
- Output paths within the build tree: `build/reports/sbom/bom.{json,xml}`.

## Build wiring

The SBOM is produced by the [`org.cyclonedx.bom`](https://github.com/CycloneDX/cyclonedx-gradle-plugin)
Gradle plugin. It is applied at the root via
[`gradle/sbom.gradle`](../../gradle/sbom.gradle); the file declares the
plugin, configures it, and hooks the `cyclonedxBom` task as a
dependency of `buildGhidra`. The release zip cannot be assembled
without producing an SBOM first.

## What's included

The SBOM enumerates the `runtimeClasspath` configuration across the
root project and every subproject. That is:

- Every JAR under `Ghidra/Framework/*/lib/`.
- Every JAR under `Ghidra/Features/*/lib/`.
- Every JAR under `Ghidra/Processors/*/lib/`.
- Every Gradle-resolved external dependency (versions pinned via
  `gradle/support/fetchDependencies.gradle`).

Test-only and build-time dependencies are not in scope; consumers
care about what ships, not what built it.

## What's not included

- Native binaries (the C++ decompiler, the native loaders) — these
  carry no Gradle dependency graph. The SBOM lists them as
  components without a dependency tree; their content hashes are
  recorded so an integrity check is still possible.
- Python packages bundled with PyGhidra — those are tracked
  separately by PyGhidra's own packaging (see
  `Ghidra/Features/PyGhidra/`); the SBOM points to that manifest.

A future PR may unify these into a single aggregated SBOM.

## Verification

A user verifies an SBOM matches the release by:

```
sha256sum -c support/sbom/bom.json.sha256
```

The `.sha256` file is generated by the release workflow and shipped
alongside the SBOM. Combined with the [binary signing](../security/BINARY_SIGNING.md)
([Rec 17](../security/BINARY_SIGNING.md)) of the release zip, the
chain is:

1. Release zip is Cosign-signed.
2. Inside the verified zip, `support/sbom/bom.{json,xml}` are the
   ground truth.
3. Every JAR's hash in the SBOM matches the JAR shipped.

## Why CycloneDX and not SPDX

Both are valid OSS-SBOM standards. CycloneDX:

- Lighter learning curve for downstream tooling (smaller schema).
- First-class Gradle plugin already mature.
- Better-supported vulnerability cross-reference (`CycloneDX-VEX`
  for declaring "this CVE is fixed in this version" — a feature
  the project will need as Rec 12 (CVE policy) lands).

If a major downstream consumer requires SPDX specifically, we can
add a second emit; the plugin supports both.

## Running locally

```
gradle cyclonedxBom
# SBOM files appear at build/reports/sbom/bom.{json,xml}
```

Or piggyback on the release build:

```
gradle buildGhidra
# SBOM files are inside build/dist/ghidra_<version>.zip
# at support/sbom/bom.{json,xml}
```

## Maintenance

- The CycloneDX plugin version is pinned at the top of
  `gradle/sbom.gradle`. A version bump is its own PR; we don't
  silently upgrade since the schema can shift.
- The `runtimeClasspath` configuration drives the SBOM; if a new
  module is added that doesn't follow the standard configuration
  layout, its dependencies will silently miss the SBOM. The
  distribution test (Rec 22, when it lands) includes an SBOM
  presence check.
- An SBOM that is empty or fails to enumerate ≥10 components is a
  build failure. The check lives in [`gradle/sbom.gradle`](../../gradle/sbom.gradle)
  as the `sbomSanityCheck` task which runs `finalizedBy cyclonedxBom`.
  The 10-component threshold catches the failure mode where a
  Gradle dep configuration was silently renamed and the SBOM
  enumerates nothing useful.

## Coordination with vulnerability response

The SBOM is the artifact downstream security teams scan. When we
ship a CVE fix ([Rec 12](../security/CVE_POLICY.md)), the advisory
references the affected version range and the SBOM tells the
scanner exactly which JAR moved. The two pieces compose.

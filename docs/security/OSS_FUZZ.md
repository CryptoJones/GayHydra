# OSS-Fuzz Integration

*Addresses Rec 13 of the 2026-05-21 principal-architect audit.*

## Why this exists

The C++ decompiler is the single highest-EV fuzz target in the
codebase: **187k LOC** parsing untrusted p-code and XML input, with
**~2,740 raw `new`/`delete` sites** and exactly one `unique_ptr`
import in the whole tree. The audit identified zero public fuzz
harnesses. Google OSS-Fuzz is free for open-source projects and
includes 24/7 fuzzing infrastructure, automatic crash triage, and
private 90-day embargo windows on disclosed findings.

This document is the integration plan. The scaffold lives at:

- `Ghidra/Features/Decompiler/src/decompile/cpp/fuzz/` — harness sources.
- `.github/oss-fuzz/` — OSS-Fuzz project files (Dockerfile, build.sh,
  project.yaml) to be merged into google/oss-fuzz as `projects/ghidra-decompiler/`.

## Initial fuzz targets

| Target | Entry point | What it hits |
|---|---|---|
| `fuzz_xml` | `xml_tree(istream&)` | XML parser (`xml.cc`) — loaded archives, sla files, the decompiler's XML IPC variant. |
| `fuzz_marshal` | `Decoder::open(...)` | Binary marshal protocol (`marshal.cc`) — the Java↔C++ IPC. |
| `fuzz_loadimage_xml` | `LoadImageXml::loadImageXml(...)` | XML load-image format — parses attacker-shaped binary metadata. |
| `fuzz_ipc_schema` | `decode_*()` (Rec 34 codecs) | FlatBuffers IPC schema decoders (`schema/ipc_*_codec.h`, #34-9) — the v1 replacement for the marshal/XML IPC. Header-only; drives every worker-side `decode_*_request`/`_response` against one buffer and relies on the verify-before-read contract. |

Each target is one `.cc` file in `cpp/fuzz/`, follows the libFuzzer
contract (`int LLVMFuzzerTestOneInput(const uint8_t*, size_t)`),
and produces a standalone executable when built via
`Makefile.fuzz`.

Sleigh `.slaspec` fuzzing (Rec 40) is **out of scope** for this rec.
It needs a separate harness driving the Sleigh compiler frontend and
benefits from differential fuzzing against a reference; that work
ships under [SLEIGH_FORMAL_AND_FUZZ.md](../sleigh/SLEIGH_FORMAL_AND_FUZZ.md).

## Local build & run

Prerequisites:

- Clang with libFuzzer support (`-fsanitize=fuzzer`).
- A build of the decompiler's C++ object files (`make -C cpp`).

Build a single target:

```
cd Ghidra/Features/Decompiler/src/decompile/cpp/fuzz
make -f Makefile.fuzz fuzz_xml
```

Run with a corpus:

```
mkdir -p corpus_xml seeds_xml
# put a few small valid XML files into seeds_xml/
./fuzz_xml -max_total_time=600 corpus_xml seeds_xml
```

Build with sanitizers (the default for OSS-Fuzz; recommended locally):

```
make -f Makefile.fuzz ASAN=1 UBSAN=1 fuzz_xml
```

This builds against the [ASAN/UBSAN CI variants](../decompiler/asan-ubsan-ci.md)
([Rec 15](../../.github/workflows/decompiler-sanitizers.yml)). Findings
should be reproducible under both the OSS-Fuzz sanitizers and the
ASAN/UBSAN CI job.

## Seed corpus

The seed corpus is the bootstrap of useful inputs. For each target:

| Target | Seed source |
|---|---|
| `fuzz_xml` | A trimmed selection from `Ghidra/Features/Decompiler/src/decompile/datatests/` (XML test data the decompiler already parses). |
| `fuzz_marshal` | Captures from real Java↔C++ traffic (committed under `cpp/fuzz/seeds/marshal/`, generated by a one-time capture script). |
| `fuzz_loadimage_xml` | A few `Ghidra/Test/IntegrationTest/data/` PE/ELF/Mach-O sniff samples. |
| `fuzz_ipc_schema` | Valid v1 payloads emitted by the codec encoders (e.g. the buffers the `testipc_*_codec.cc` round-trips build), dropped under `cpp/fuzz/seeds/ipc_schema/`. |

Seeds live under `cpp/fuzz/seeds/<target>/` and are committed.
OSS-Fuzz reads them at build time via `build.sh`.

## Sanitizer combinations

OSS-Fuzz runs each target under:

- AddressSanitizer (ASAN) — heap overflows, use-after-free, leaks.
- UndefinedBehaviorSanitizer (UBSAN) — signed overflow, null deref,
  divide-by-zero, bad cast, alignment.
- MemorySanitizer (MSAN) — uninitialized read. Requires
  instrumented dependencies (libc++); a known cost.

The decompiler's existing `Makefile` had ASAN/UBSAN flags commented
out (see [Rec 15](../decompiler/asan-ubsan-ci.md)). Re-enabling them
in CI is a prerequisite to this rec being maximally useful.

## Embargo and disclosure

OSS-Fuzz findings are disclosed to maintainers privately and
embargoed for 90 days. The embargo timeline is compatible with the
[Security Policy](../../SECURITY.md) and the [CVE Policy](CVE_POLICY.md):

1. OSS-Fuzz emails the maintainers (the addresses in
   `project.yaml`).
2. The reporting maintainer opens a draft GHSA advisory immediately
   per [CVE_POLICY.md](CVE_POLICY.md).
3. The fix lands on master under the same embargo (private fork
   while fixing; merged after the patch is ready).
4. After 90 days (or sooner if all conditions of
   [SECURITY.md](../../SECURITY.md) embargo policy are met), the
   OSS-Fuzz bug becomes public.

## OSS-Fuzz submission checklist

To go live on OSS-Fuzz:

- [ ] Harness sources committed under
      `Ghidra/Features/Decompiler/src/decompile/cpp/fuzz/`.
- [ ] `Makefile.fuzz` builds each target locally with libFuzzer.
- [ ] Seed corpus committed under `cpp/fuzz/seeds/<target>/`.
- [ ] `.github/oss-fuzz/Dockerfile` builds against an upstream
      Ubuntu base.
- [ ] `.github/oss-fuzz/build.sh` produces the harnesses and copies
      them to `$OUT/`.
- [ ] `.github/oss-fuzz/project.yaml` lists at least two
      maintainer email addresses for vulnerability email.
- [ ] PR to <https://github.com/google/oss-fuzz/> adding
      `projects/ghidra-decompiler/` with the same three files.
- [ ] First successful build and trial-run on the OSS-Fuzz
      infrastructure.

## Maintenance commitment

Once integrated, we commit to:

- Acknowledging OSS-Fuzz crash reports within the
  [SECURITY.md](../../SECURITY.md) response-target windows.
- Keeping the build green. OSS-Fuzz disables a project when its
  build fails for a sustained period; we treat a red build as a
  P1.
- Reviewing newly-added decompiler entry points for fuzz coverage
  in the same PR that adds them.

## Open questions

1. Should we also fuzz the Sleigh-compiled SLA binary loader
   (different surface from `xml.cc`)?
2. Should the marshal harness use a corpus captured from real
   decompiler runs or from synthetically generated frames?
3. What is the right policy for vendor-encumbered seed corpora
   (e.g., proprietary firmware images that exercise a loader)?
   For now we use only open-source samples.

These are tracked in `docs/security/oss-fuzz-followups.md` once
the initial integration lands.
